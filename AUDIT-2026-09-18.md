`target_dir.glob("*.json")` — depth 1 — so stale *nested* source documents were
never pruned and their directories were never removed. Deletions could not
propagate for sources at all.

### Fix (this session)

* `src/omnisource/api_v3.py`
  * new `SAFE_DOC_ID_CHARS` + `safe_doc_id()` — flattens any id to a single
    segment of `[A-Za-z0-9._-]`; `""`/`"."`/`".."` collapse to `source`;
  * source documents now keyed by `slug` first, sanitised `id` as fallback,
    with `-2`/`-3`… suffixes on collision (same convention `_unique_ids` uses
    for apps);
  * `_unique_ids` routes app ids through `safe_doc_id` too — a no-op today
    (measured: 130 apps, 0 unsafe slugs, 0 nested app docs) and a guard
    against the same class of bug;
  * docstring corrected: `/api/v3/sources/<slug>.json`.
* `scripts/build_api_v3.py` — prune is now `rglob`-based, compares
  `path.relative_to(out_dir).as_posix()` against the document keys, and removes
  the directories it empties (`contextlib.suppress(OSError)`).

## 10. Second round (same day): the reader-reported scroll bug, and F2/F3/F6

### 10.1 The reported symptom, and what actually caused it

Report: *"when scrolling one website suddenly it starts refreshing and goes to
the first page."*

There is no reload path in the current code — I checked before assuming one:
`location.reload()` appears twice in `js/core.js`, and line 791's occurrence is
inside the comment block that documents the **removed** auto-reload
("Service-worker updates are opt-in, never automatic"), while line 833's is
inside `applyServiceWorkerUpdate()`, reachable only from the reader pressing
Update. `sw.js` only calls `self.skipWaiting()` from its `install` handler and
in response to `omnisource-skip-waiting`; neither reloads a page. No
`http-equiv="refresh"` exists on any page except `compare.html`, which is an
intentional redirect stub to `/compare/`.

The real mechanism is a **scroll-position yank**, not a refresh.
`js/site.js` re-pins a deep-linked section after every feed-driven render
(`refreshPage()` -> `repinHash()`), because the home page un-hides whole
sections above the catalog as their feeds land. The re-pin was disarmed only by
`wheel`, `touchmove` and the scroll keys. **A scrollbar drag and middle-click
autoscroll raise none of those events**, so a reader who scrolled that way
stayed "armed": the next deferred feed to land — they arrive for several
seconds — called `scrollIntoView()` on the deep-linked section and pulled the
catalog back to its own top. On a phone (Android's scrollbar thumb) and on a
desktop scrollbar alike that reads exactly as the page refreshing and returning
to the first section.

Reproduced in jsdom, pre-fix, by `tests/js/scroll_pin.cjs`:

```
"checks": 9, "failed": 3
  - a reader who scrolled by scrollbar is not yanked back by a late feed:
    the page re-pinned after the reader scrolled away: ["catalog"]
  - and stays put for every feed after that:
    further re-pins: ["catalog","catalog"]
  - stableScroll falls back to <main> when the render replaces the landmark:
    expected one correction to 800 via <main>, got []
```

### 10.2 Fixes

* `js/site.js` — `armHashRepin()` now separates two lifetimes: watching the
  reader's movement ends the *current* re-pin, while `hashchange` stays
  listenable for the whole 25 s window and re-arms the watch. A `scroll`
  listener ends the re-pin unless `repinOwnScroll` is set; `repinHash()` sets
  that flag and clears it on the next frame (scroll steps run before rAF
  callbacks, so our own event is consumed there, and a no-op `scrollIntoView`
  cannot swallow the reader's *next* scroll).
* `js/core.js` — `OS.stableScroll` measured a deep landmark and its section,
  and if the render replaced **both** it computed no delta and made **no
  correction at all** — precisely the multi-thousand-pixel jump it exists to
  prevent on engines without scroll anchoring. It now measures `<main>` too and
  uses it as a last resort.

Both directions are pinned, so the test cannot pass vacuously: one check asserts
a late feed *does* re-pin while the reader has not moved, and another asserts a
new deep link after a reader scroll is honoured again. The latter was rewritten
twice: the first version passed pre-fix (a scrollbar scroll never disarmed
anything, so `hashchange` was still live), and only discriminated once the
disarm was done with `wheel`, which every version honours.
